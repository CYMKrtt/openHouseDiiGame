# A Little World of Companies — M5 development

This repository includes the accepted M2 browser-local mock, conditionally accepted M3 multiplayer core and M4 assignment/reveal, and the M5 Next Round implementation. M3 and M4 were tested against a dedicated disposable Supabase development project on 2026-11-08.

## Run

Use Node.js, run `npm ci` and then `npm run dev`. Open `/` for the player flow and `/host` for the separate mock Host screen. The Host mock password is displayed on the screen and does not protect data. The labelled prototype controls add or disconnect simulated players and reset local mock data; they are for review only.

`npm run build`, `npm run typecheck`, `npm run lint`, and `npm test` run the standard checks. `npm run test:visual` starts the app and a read-only server for the reference HTML, then captures and compares baseline, actual, and diff images under `test-results/`. The Playwright configuration currently expects Microsoft Edge at its default Windows installation path. Visual checks use a reduced-motion browser context for stable matching of corresponding states and a 2% pixel-difference threshold; transition behavior needs additional visual review at normal motion. They do not modify approved references.

## Structure and boundaries

`src/components/` contains React screens and event handlers; `src/art/` contains JSX copies of approved SVG art; `src/styles/` contains the approved page styles. `src/mock/` implements the replaceable localStorage/sessionStorage simulation. Mock state is shared only among tabs on this browser and has no concurrency or security guarantees. Company labels and colors are configured in `src/lib/companies.ts`. Internal IDs remain `tech`, `design`, and `ecommerce`.

`reference/prototypes/` contains the read-only approved originals. Do not modify them. LINE Seed Sans TH is not included because no licensed asset was provided. The original fallback fonts remain, and a visual review is required after the approved font is obtained. The B01 original placeholder remains pending replacement; labels Tech / Design / E-Com are provisional. Host/error supplemental copy remains subject to review.

Do not use this development configuration for a live event or deploy it. M5 remains outside authorization.

## M3 development setup and validation

Server mode is separate from the M2 mock. Development defaults to mock; set `NEXT_PUBLIC_SESSION_MODE=server` to exercise the server-backed screens. Production builds default to server mode and fail closed when unconfigured. Staging requires a protected deployment and a dedicated test database. Live events require release approval.

1. Create or designate a **non-production Supabase project**. Do not run these migrations against a production project. After the owner confirms the project is isolated and disposable, run `node scripts/m3-preflight.mjs` followed by `node scripts/m3-migrate.mjs` to apply the three migrations to a verified empty project. Both scripts require `M3_TEST_DISPOSABLE_DATABASE=yes` and matching app/database project references; the migration runner refuses nonempty public/Auth/Storage data. Run `node scripts/m3-verify-schema.mjs` to check RLS, privileges, constraints and the Realtime publication. The scripts never run automatically. They were run successfully on the designated disposable development project on 2026-11-08.
2. Copy `.env.example` to `.env.local`. Set `APP_ORIGIN` to the exact local app origin (for example `http://localhost:3000`); set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to the development project URL and server secret key (or legacy service-role key) in this local file only. Set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` to its public project URL and anon/publishable key. Never put service-role keys in a `NEXT_PUBLIC_` variable or share secrets in chat.
3. After saving the API keys, run `node scripts/configure-private.mjs` from this directory in an interactive terminal. Paste the Session pooler connection string when prompted, then enter the database password and choose a development-only Host password. Input is hidden; the helper verifies the project match, URL-encodes the password, creates a dotenv-safe scrypt verifier and writes those private settings directly to `.env.local` without displaying them. When an interactive terminal is unavailable, `node scripts/configure-private-web.mjs` serves a temporary form bound to `127.0.0.1`; it checks the database connection before saving and closes after one success. This alternative requires a non-secret `M3_SESSION_POOLER_TEMPLATE` containing `[YOUR-PASSWORD]` in `.env.local`. Restart the dev server after setting variables. Do not paste passwords, keys or hashes into chat.
4. Start `npm run dev` and use separate browser contexts to test player Join, refresh, presence, and Host login. `npm run test:db`, `npm run test:api`, and `npm run test:server` exercise local checks; these do not replace a real Postgres/Supabase concurrency and authorization test.

Presence uses 15-second heartbeats and a 45-second server-time lease as development defaults. Expiry is evaluated at query time; a 2-second poll catches expired leases and start events even without a Realtime update. Explicit disconnect is best effort. Measure actual silent-loss and background-browser detection before release.

On 2026-11-08 the dedicated project passed the empty-data preflight, migrations, schema and privilege checks, 16 concurrent HTTP Join requests (15 accepted, one rejected), duplicate registration, multi-tab presence, disconnect/reconnect, expiry, RLS, Realtime notification, Host authorization and revocation. `npm run test:integration` is the destructive capacity test and requires an empty session; it leaves 15 reserved seats. `node scripts/m3-realtime-probe.mjs` verifies a Realtime revision event independently. `node scripts/m3-host-login-check.mjs` tests positive password login using an ephemeral test-only verifier on a separate local app port. The Owner also entered the locally chosen Host password into actual server mode and saw 15/15 seats; one active Host session was independently observed in the database without reading its token. `node scripts/m3-browser-check.mjs` checks server-mode Lobby and Host at 320×640, 390×844 and 1440×900 and verifies Lobby polling while Realtime is blocked. `node scripts/m3-visual-check.mjs` compared server-mode Lobby with its approved prototype at the same state: 0.24%, 0.15% and 0.08% pixels differ at those three sizes. The browser and visual checks expect the 15 synthetic `Concurrent` players created by the capacity test. `node scripts/m3-reset-concurrency-fixture.mjs` removes only that verified synthetic fixture if a retry is needed; it stops if other player data or an active Host session is present.

Remaining M3 review risks: the first real capacity run filled 15 seats but failed at the subsequent Realtime assertion before later API checks. A separate revision-event probe passed, and the full rerun passed after the test emitted an extra revision notification. Full-load Realtime delivery is not independently characterized, so polling remains necessary. Request limiting and Host login throttling have not had a sustained load test on the actual Supabase plan; assess edge abuse controls and quotas before exposure. Presence was verified with server-time expiry and a blocked-Realtime poll, but longer silent-loss and background-browser timing remain to be measured before release. The accepted M2 LINE Seed Sans TH font, normal-motion and broader accessibility review also remain open before release.

For a real capacity check, use a separate **empty, disposable** test database with the M3 migrations applied. The owner must explicitly confirm the project is disposable and set `M3_TEST_DISPOSABLE_DATABASE=yes`. Then run `npm run test:integration`. This test submits 16 concurrent Join requests through the local API, intentionally consumes all 15 seats and does not delete them. Do not point it at an event database or a project containing participant data. Without both variables the test is skipped.

## M4 development and review

Apply `node scripts/m4-migrate.mjs` only to a verified disposable development project with M3 already installed. It refuses unexpected player, Auth, or Storage data. The two M4 migrations create immutable balanced assignments, a one-time atomic Host/Auto start, and a shared reveal timestamp. Existing development projects that had the original two-second lead may apply `node scripts/m4-apply-lead.mjs`; that helper checks the old function and synthetic fixture before changing it. The current lead is five seconds before the approved four-second star, allowing Realtime or two-second polling clients to fetch the start timestamp. Company labels remain provisional in `src/lib/companies.ts`; B01 copy remains pending.

`node scripts/m4-verify-schema.mjs` checks M4 RLS, immutable assignment trigger, metadata constraint, and start RPC privileges. `npm run test:db` covers N=1–15 balance, offline seats, Auto and Host eligibility, immutable retries, and join rejection. Real local API tests on the owner-confirmed disposable fixture used `scripts/m4-integration-check.mjs` for 15-context Auto Start and `scripts/m4-host-check.mjs` for two simultaneous Host confirmations with one online player. `scripts/m4-browser-check.mjs` captured server Reveal/Host layouts at 320×640, 390×844, and 1440×900 and compared Reveal spin/result with approved HTML. These scripts are fixture-specific, can consume or reset synthetic seats, and must not run against valuable data.

The first 15-context run observed 6,060 ms start skew with five-second fallback polling and a two-second reveal lead. After changing polling to two seconds and lead to five seconds, the single follow-up run observed 548 ms skew with 15 assignments (5/5/5), replay and late-join rejection. A separate one-browser replay measured a 3,998 ms Star with the original commit unchanged. The follow-up run used a local production-mode app and Edge background-timer controls, so it does not isolate which change fixed the skew or prove venue Wi-Fi timing. M4 was conditionally accepted. Venue Wi-Fi timing, Realtime delivery under 15-client load, and a direct Host versus Auto race remain staging checks.

## M5 Next Round

Apply `202611080003_m5_next_round.sql` after the M3 and M4 migrations in the authorized test/staging database, then use the matching M5 app build. The migration retains the original round and participants and retires the unscoped M3/M4 write RPCs, so the older app cannot write once this migration is installed. Run the M3/M4 fixture scripts only against a pre-M5 disposable database. The old destructive reset helpers refuse the M5 schema.

Host can confirm **Next Round** after the server's four-second Reveal window ends. One atomic rotation ends the current round, revokes its presence leases, and opens a fresh round at the same QR URL. Participants need to submit Join again. The Host session remains valid. The database keeps previous rounds, participants, and assignments.

Run `node --test tests/database/m5-next-round.test.mjs` to check migration, history, stale requests, and start eligibility. Use `node tests/integration/m5-next-round-browser.mjs` for the isolated browser and API check. It uses embedded PostgreSQL and loopback only. Before staging sign-off, verify simultaneous rotation with separate PostgreSQL connections and repeat the QR and Reveal flow on mobile using the protected staging URL.

## M6 Quiz assignment

Players answer a five-question quiz and see their company as soon as they submit, without waiting for others: `/` Join → `/quiz` → `/reveal` (the original 4-second star reveal plays for each player). The company comes from the answers instead of a random draw, and the result page shows the score split, why the track fits, skills to practise and related CAMT majors. `/lobby` now only forwards old links.

- Host sees each player's company live. The Host button is now **ปิดรอบ** (close round): it stops new joins and gives players who have not finished the least-filled companies. The round also closes by itself once all 15 seats have a result. Next Round works as before after closing.

- After the reveal, a card shows the company's mini-game from the team's Canva decks (Tech: CODE อ่านกัน, Design: จับผิดภาพ, E-Com: Circus Pitching). Copy is in `companyActivities` in `src/lib/quiz.ts`; themes are in `src/styles/activity.css`.
- Question and result copy: `src/lib/quiz.ts`. Every track lists CAMT's DII (Digital Industry Integration) as the related major (`camtMajors`).
- Scoring and assignment rules (pure functions): `src/lib/quizScoring.ts`, tested by `npm run test:unit`. DEV → `tech`, DESIGN → `design`, BIZNET → `ecommerce`. A clear winner is never moved; a 2-2-1 tie uses question 5, then question 1, and goes to the tied company with fewer members at the moment that player submits (first come, first served). Players who did not finish the quiz fill the smallest companies. Company sizes may be unequal.
- Option order is shuffled per player and stays the same on refresh. In-progress answers are kept in `localStorage` (`lw-quiz:<round>:<player>`).
- Server mode: apply `supabase/migrations/202611090001_m6_quiz_assignment.sql` after M5, only on an authorized disposable test/staging database. It adds `m6_quiz_answers`, `m6_submit_quiz`, assigns the company inside `m6_submit_quiz`, turns `m5_start` into close round (same signature; Host close needs one reserved player, Auto closes only when all 15 seats have a result) and adds `quizAnswers` to the player's own state. Host state does not include answers. `npm run test:db` covers it on PGlite; `node tests/integration/m5-next-round-browser.mjs` runs the full server-mode flow including the quiz.

## Nextopia theme

Player pages (`/`, `/quiz`, `/reveal`, `/lobby`) follow the official CAMT NEXTopia Open House 2026 poster ("Design your future"): a night city with neon orange, violet and cyan light, chrome lettering and glowing glass room-cubes. A stepped night sky with a neon pixel skyline (`src/components/NextopiaSky.tsx`) sits on every player page, and its windows switch to the company colour when the result is revealed. The landing hero (`src/art/nextopia.tsx`) is a pixel-art version of the poster's stacked glass rooms, one per company. Styles are in `src/styles/nextopia.css`, loaded after each page's original sheet; the Host dashboard only gets colours and type from `src/styles/host-nextopia.css`. Fonts come from `next/font/google` in `src/app/layout.tsx` (Bai Jamjuree for headings, IBM Plex Sans Thai Looped for text, Silkscreen for pixel labels); the build downloads them, so it needs internet access. This replaces the approved prototypes' look, so `npm run test:visual` is expected to differ from the reference HTML, and the earlier LINE Seed Sans TH decision should be reviewed.
